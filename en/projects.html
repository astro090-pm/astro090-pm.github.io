Roadmap: Weekend Planner

What is done, what I'm working on, what's next and what I dropped — and why. More in the repository docs

User jobWhen on Friday I'm thinking about what to do with my kid at the weekend, I want an hour-by-hour plan that accounts for weather and budget in a minute, so that I don't spend half an hour switching between listings, maps and the forecast.

Done · MVP in 3 days

  • 3 agents over A2A: orchestrator, scout, critic
  • My own MCP server and a browser agent
  • 32 eval cases and model comparison
  • Prices, addresses and times in the plan come from code, not the model
  • Events and metrics: activation, 👍, return 7d

Now

  • First users: the goal is 20–50 people who received a plan
  • A separate link per channel to see where people come from
  • Plans with 👎 → new eval case → fix → re-run

Next

  • Streaming and caching: answers in seconds, not tens of seconds
  • Personalization based on rating history
  • Online evals on real conversations
  • Tracing by stage and alerts on rising fallbacks
  • A/B tests of prompts and models with guardrail metrics
  • Ticket purchase as a tool — with user confirmation

Dropped

  • One agent for everythingwhere the path is known, predictable code is better: each stage can be measured and fixed separately
  • The model writes prices and addressesit picks ids and code fills in the facts, so the plan can't invent places
  • The official A2A SDK~150 readable lines were enough for a prototype; the contract matches the spec
  • An LLM critic that triggers fixesLLM review can be wrong, so it only advises; code checks do the blocking
  • Lock-in to one providerthe model is switched with one setting, and evals compare models from different companies

User stories

doneAs a user whose plan didn't fit, I want one button for another option or a cheaper one, so that I don't have to write the request again.

Acceptance criteria

  • every plan has “🔁 Another option” and “💸 Cheaper” buttons
  • a change can also be written as plain text
  • the revised plan passes the same checks as the first one

Metric

refine rate — revisions per delivered plan

doneAs a parent, I want the bot to account for my child's age and the weather, so that we don't end up somewhere a child isn't allowed, or in the rain.

Acceptance criteria

  • only age-appropriate items get into the plan
  • in rain — only indoor places
  • code checks this, not the model; there are eval cases for kids and rain

Technical decisions

How to orchestrate

Options

  • one agent for everything
  • a rigid workflow
  • ✓ a workflow + an agent where the path isn't known in advance
Why
Where the path is known (parse → plan → check), predictable code is better; where decisions are made on the fly (which tools, in what order), an agent.
Trade-off
Less flexibility on known stages, but each stage can be measured and fixed separately.
Product role
Project author: my decision.

How to prevent invented places and prices

Options

  • the model writes the whole plan
  • ✓ the model picks ids, code fills in the facts
Why
The model cannot “say” a price or an address: after the plan is drafted, code overwrites the name, address, link and price with the candidate's data.
Trade-off
Free text (explanations, tips) is still written by the model, so evals check it.
Product role
Project author: my decision.

Who blocks a faulty plan

Options

  • an LLM critic
  • ✓ code checks; the LLM critic only advises
Why
Deterministic checks are stable and cheap, while LLM review can be wrong.
Trade-off
Code can't check subjective things (“is this what was asked”) — the LLM rates them, but can't block.
Product role
Project author: my decision.

Protocol between agents

Options

  • the official A2A SDK
  • ✓ my own minimal A2A
Why
About 150 fully understandable lines were enough for a prototype.
Trade-off
I maintain it myself; but the contract matches the spec, so switching to the SDK only touches the a2a/ package.
Product role
Project author: my decision.

Model lock-in

Options

  • one provider's SDK
  • ✓ my own layer over REST: OpenAI-compatible API and GigaChat
Why
The model is switched with one setting, and evals compare models from different companies on the same cases; full control over retries and fallbacks.
Trade-off
More own code: a client per protocol and tests via a mock transport.
Product role
Project author: my decision.
