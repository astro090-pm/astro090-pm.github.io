Weekend Planner

An agentic Telegram bot that builds an hour-by-hour weekend plan in a minute: it checks the weather, events and places, stays within budget and takes children's ages into account.

Status: Prototype The MVP was built in three days in October 2026, and the code is open. It hasn't been launched to real users yet, so there are no usage results so far.

Problem and context

To plan a weekend, people spend 30–40 minutes switching between event listings, maps and the weather forecast. This is an estimate from the project brief, not a measurement.

Hypothesis: people will use and come back to a ready hour-by-hour plan made in a minute that accounts for weather, budget and children.

Audience and key scenario

People planning a weekend in their city, including with children; event data comes from KudaGo. Scenario: write to the bot “Saturday with a 6-year-old, under 3,000 roubles” and get a schedule with links; if it doesn't fit — “Another option”, “Cheaper” or a correction in your own words.

My role

The project is entirely mine: problem framing, requirements, architecture, code, evals and launch plan. I wrote the code together with an AI coding assistant.

Requirements and success criteria

  • Only real events and places found by the tools go into the plan.
  • Respecting budget, children's ages, excluded categories and weather.
  • Resilience to model and data source failures.
  • Product metrics are instrumented: activation, time-to-value, return 7d, 👍 share, refine rate. Target values haven't been set before launch.

Architecture and data flow

  1. The user writes to the Telegram bot; the orchestrator parses the request into preferences (validated JSON).
  2. A scout agent, over the A2A protocol, collects candidates through my own MCP server: weather, events, places, reading pages with a browser.
  3. The orchestrator builds a plan only from real ids; facts (names, prices, times) are filled in by code.
  4. A critic agent over A2A checks the plan: 18 deterministic checks plus an LLM review.
  5. Up to two rounds of fixes; if errors remain, the faulty items are cut.

Technologies

Python 3.13 · MCP · own A2A implementation (JSON-RPC) · Playwright · KudaGo, Open-Meteo, OpenStreetMap · any OpenAI-compatible API or GigaChat · Telegram (long polling) · Docker · GitHub Actions.

Implementation and code

Source code, setup instructions and documentation are in the GitHub repository (in Russian). Detailed architecture: ARCHITECTURE.md; first-users plan: LAUNCH_PLAN.md. There is no public demo: the bot runs locally or on a VPS with your own keys.

How quality is tested

  • 55 unit tests and CI on every commit (per the README).
  • 32 eval cases on fixed data: budget, children, rain, dates, an unknown city, off-topic and prompt injection — including one hidden on an event page.
  • Failure taxonomy, model comparison between runs, LLM-as-judge as an additional signal.

Results

Not measured: the bot hasn't been launched to real users yet. After launch, data on activation, returns and ratings will appear here.

Limitations, risks and security

  • Dependence on external data sources — retries, caching, a circuit breaker and a fallback source for places.
  • Prompt injection via web pages — the text is marked as untrusted, and only objects from the registry of found items can enter the plan.
  • SSRF — the browser agent opens only public addresses.
  • Cost — limits on agent steps and plans per user per hour.

Conclusions and next steps

The main design takeaway: the model chooses, the code is responsible for facts — this protects against hallucinations more reliably than prompts. Next: launch to first users, streaming responses and caching to reduce latency, per-stage tracing, online evals on real conversations.
