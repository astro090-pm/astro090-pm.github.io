bolz.dev: an MCP connector that lets AI agents take real-world actions

Key resultMVP in August 2025

Role
Co-founder & CPO
Where
bolz.dev, Dubai
When
2025 (startup)
Product
a Model Context Protocol (MCP) platform: services connect once, and AI agents find, book and pay for them on the user's behalf
Stage
MVP built in August 2025
Models
B2B (services and e-commerce) and B2C (AI assistant users)
Predecessor
bolz.tech — sharing ecosystem

User jobs (JTBD)

  • 🙂User

    When I ask an AI assistant to buy or book something, I want to go from request to payment in one conversation, so that I don't follow links or fill in forms.

  • 🤖AI agent

    When a user asks me to take an action, I want to call a tool with live prices and payment, so that I finish the job instead of handing over a link.

  • 🏪Service

    When customers increasingly come through AI assistants, I want to connect once and appear in agents' answers, so that I don't lose those customers.

Problem

AI agents can search and recommend, but rarely finish the job:

  • Agents: almost always send the user to a website link to complete the action; the best models succeed at real-world tasks less than half the time (MCP-Universe benchmark).
  • Services: most companies risk not appearing in agent answers at all.
  • Users: buying a flight via an AI agent today takes longer than doing it yourself — the agent imitates a human: search, links, forms.

Solution

Bolz Connector sits between agents and services:

  • services connect once via plugins, a web interface or REST API;
  • agents get normalised JSON, live prices and functions "search / reserve / confirm / refund / pay";
  • users go from request to payment in a single conversation.

We designed two scenarios — a marketplace ("find a housewarming gift under $100") and taxi ("call a Comfort car, avoid traffic"). Quality is measured with execution-based evals: success is a completed action, not a model's answer.

What I did as CPO

  • Framed the problem from three sides — services, agents, users — and the value proposition for each.
  • Designed user flows from chat request to confirmed payment.
  • Described the architecture: agent → MCP server with service connectors → action → result check.
  • Analysed competitors: direct (Notte, Firecrawl) and indirect (Google's own AI services, Grab, Loman.ai).
  • Built the go-to-market: connector in Claude and ChatGPT, API integrations, sandbox and tutorials for developers.

Technical decisions

How an agent takes action

Options

  • the agent repeats human actions on websites (scraping, clicks)
  • ✓ connectors to service APIs via MCP
Why
Through websites an agent is slow and unreliable: the best models complete real tasks less than half the time. APIs give live prices and order and payment functions.
Trade-off
Each service has to be connected, so coverage grows with integrations.
Product role
As CPO I described the architecture and analysed competitors: Notte and Firecrawl work through websites.

How to measure agent quality

Options

  • by the text of the answer
  • ✓ by the completed action
Why
The user needs a purchased ticket, not a nice answer.
Product role
I set the success metric: a paid order.

What this case shows

A product at the core of the agent layer: MCP, agent tools, outcome-based evaluation and product metrics for agentic scenarios.

What I learned

  • Agent quality should be measured by the completed action (a paid order), not by the text of the answer.
  • The value has to be framed for three sides at once: services, agents and users.
